## Exact source-pointer allocation

A prediction_file allocation list associates each actually imported source-value JSON pointer with its generated computed Evidence ID, unique in both directions within that source. Evidence.prediction_origin must name the same file and pointer, and every allocation must resolve to that corresponding Evidence. This is appropriate narrow importer bookkeeping. It prevents a pointer-only change to an equal-valued neighboring canonical record from passing solely because all scalar/context fields compare equal. Distinct identical raw rows remain distinct records and receive distinct IDs; they are not deduplicated or treated as independent scientific replicates.

The reciprocal links are an association cycle in the reference graph, not a causal provenance cycle. A prediction_file does not scientifically derive from its extracted Evidence. Neither side authenticates the external model run or assigns a new molecular identity. Validate the indexed graph in both directions independently of entity order; do not interpret allocation as a causal DAG or require a topological export order.

For a reviewed valid subset, allocate exactly the Evidence actually saved from that file. Raw invalid/excluded records remain retained and inspectable but are not missing allocation dependencies. A missing/duplicate allocated pointer, repeated allocated Evidence ID, unknown target, wrong kind/type/project, Evidence with no matching allocation, allocated Evidence with no matching origin, or pointer targeting an unsupported/non-value field rejects the atomic import. Repeated imports can create distinct new source and Evidence records; uniqueness must not silently deduplicate equal observations across independently saved source entities.

Detection claims must remain precise: a changed origin against an unchanged allocation is inconsistent and detectable. If an external bundle changes both allocation and origin consistently, validation of a fresh store cannot establish their historical truth from those mutually agreeing fields alone. Existing append-only storage prevents changing an already stored association under the same ID. A self-consistent new imported package remains recorded attestation, as the clarified ADR explicitly states; it is not authenticated external row identity or tamper-proof external history.

## Complete-project transport ceiling

Applying the existing 32MiB complete JSON-escaped request envelope before persistence is consistent with J08's requirement that accepted data can be exported and reimported. Covering Store.import_bundle and the legacy Store.save_shortlist append path closes a real bypass. Preview should check the complete proposed project plus dependencies before approval, and authoritative save must recheck after incorporating current stored data. Measure actual UTF-8 bytes of the interoperable complete awx payload, including its project/schema wrapper and escaping, rather than just source text length or character count.

The limit is a documented storage/replay capability boundary, not a changed scientific threshold or sharing policy. Existing oversized records, if present, must remain readable/exportable without deletion, truncation, splitting or automatic migration. New appends may be explicitly blocked with a clear capacity explanation. Do not report such a legacy project as passing replay under the bounded request limit. Within-limit legacy records and exact Decision snapshots must keep their existing behavior. No generalized archive/chunking system is justified by this clarification.

## Required implementation checks added by this clarification

1. Two identical canonical rows allocate distinct Evidence IDs. Reorder serialized entities: replay succeeds unchanged. Change one origin pointer only: reject atomically. Change one allocation only, omit an allocated Evidence, duplicate a pointer/ID, or add an origin lacking the reverse association: reject atomically. Check separately that coordinated internally consistent new package metadata is never labelled authenticated.
2. Use a reviewed subset containing valid identical rows and invalid raw rows. Allocate only the actually saved Evidence; full raw content, QC and valid pointer identities remain intact through fresh replay. No phantom Evidence is demanded for excluded source rows.
3. At the transport boundary, independently try an ordinary import and a legacy shortlist save that would move the complete project over the limit. Both must fail without writes, while the prior project remains readable/exportable. Test a prior legacy project already above the limit and one whose multibyte/escaped content makes character count underestimate actual payload bytes. No silent content reduction is permitted.
